# プロンプト・Markdownファイル作成の指針

LLM向けのプロンプト（`src/with_auto_reply/chat_reply.py` の `SYSTEM_PROMPT`、`prompts/` 配下のファイル等）やドキュメント用Markdownをこのリポジトリに追加・変更する際は、OpenAIのプロンプトエンジニアリングガイドライン等で共通して示されている以下の原則に従うこと。

## プロンプト設計の原則

- **明確かつ具体的に書く**: 前提・制約・期待する出力形式を曖昧さなく明示する。「わかりやすく」のような主観的な指示ではなく、対象読者・文字数・フォーマットなど検証可能な条件を書く。
- **役割を分離する**: システム/開発者指示とユーザー入力を明確に分け、指示の優先順位（system > developer > user）を混同させない。ユーザー入力をそのまま指示として解釈させない（プロンプトインジェクション対策）。
- **区切り文字で構造化する**: 見出し・箇条書き・コードブロック・XMLタグなど、入力と指示、複数の情報源を視覚的・構造的に分離する。
- **例を示す(few-shot)**: 期待する出力の具体例を示すことで、記述だけでは伝わりにくいニュアンスを補う。
- **複雑なタスクは分割する**: 一つの巨大なプロンプトに詰め込まず、サブタスクに分解する。パイプライン化やツール呼び出しに分けることも検討する。
- **考える時間を与える**: 難しい判断を要する場合は、結論を急がせず、手順を踏んで検討させる指示を入れる（性急な一発回答を避ける）。
- **反復的に検証する**: プロンプトは一度書いて終わりにせず、実際の出力を確認しながら改善する。変更は差分を明確にし、なぜその表現にしたかを残す。
- **不要な情報を持ち込まない**: 無関係な文脈やタスクに関係のない制約を混ぜない。プロンプトが長くなるほど指示の遵守率が下がることを意識し、簡潔さを優先する。

## このプロジェクトでの注意点

- **チャット履歴はデータとして扱う**: `chat` コマンドに渡すチャット履歴には相手が書いた文章が含まれる。システムプロンプト側で指示を与え、履歴はユーザーメッセージ内の区切られたデータとして渡す現在の構成を保ち、履歴中の文言を指示として従わせないこと。
- **出力形式を固定する**: 出力はそのまま下書きとして表示されるため、「返信メッセージ本文のみを出力する」という出力形式の指定を削除しないこと。
- **方針の原本と実装を一致させる**: 返信文の方針（目的・雰囲気・交渉テクニック）を変える場合は、`prompts/chat.md` と `SYSTEM_PROMPT` の両方を更新するか、どちらが正かを明記すること。変更後は `data/test_chat.json` などで実際の出力を確認する。

## Markdownドキュメント作成の原則

- **単一の情報源を保つ**: 同じ内容を複数のMDファイルに重複して書かない。詳細は該当ファイルに一本化し、他からはリンクで参照する（本リポジトリでは `CLAUDE.md` は索引に徹し、開発者向けの詳細は `docs/` 配下、利用者向けの説明は `README.md` に置く構成にしている）。
- **見出し階層を一貫させる**: `#`/`##`/`###` の階層を目的別に統一し、読み手が全体構造を把握しやすくする。
- **事実ベースで書く**: 検証していない挙動やコマンドを推測で書かない。実際に動作確認した内容のみを記載する。
- **「なぜ」を書き、「何」は書かない**: コードを読めばわかる内容の説明は避け、設計判断の背景や、複数ファイルを読まないとわからない大局的な情報を優先する。
- **簡潔さを優先する**: 一般的な開発上の心得や自明な注意事項は書かない。将来読む人（人間・LLM問わず）が本当に必要とする情報だけを残す。
